# 长对话稳定性增强

`long-conversation-loop` · `0.1.0-alpha.2` · OpenCode 2.4.0 服务端插件

在同一个对话里做一件很长的事时，上下文可能经过多次压缩。这个插件在原生摘要旁补回首条目标、后来实际送达的追加要求，以及有记录的执行进度。打开原会话继续工作即可，日常使用没有按钮，也无需手动粘贴第一条提示。

例如，你先说「做完推送」，后来改成「留在本机，等我验收再推送」，再问「现在做到哪了」。插件会按先后顺序保留两条约定。模型可以核对撤回发生在哪一条，以及当时记下了哪些成果。压缩之后刚刚投递的新要求仍排在续接资料之后。

## 能找回什么

| 内容 | 初版的处理方式 |
|---|---|
| 用户要求 | 按宿主的实际投递顺序记下文字。入队后取消的消息、工具输出和系统生成的提示不计入用户要求。 |
| 压缩后的主请求 | 自动附上首条、最近六条，以及最多四条含常见中英文改口或限权用语的原话摘录，重合项只显示一次。这个筛选只帮助选择引文，约定的含义仍由模型结合对话判断。 |
| 中间轮次 | `loop_recall` 可按编号向前翻或检索原文。完整查询按连续文本匹配，忽略大小写。整句没有命中时，可按空格或逗号等分隔的多个词查找，返回命中不同词数最多的原话，并标出 `matchedTerms`。同分取最近四条，按提示编号顺序显示。每条最多保存约 1,600 个 Unicode 字符，过长时保留首尾并标明省略。附件内容不归档。 |
| 阶段成果 | `loop_checkpoint` 供模型记录当前约束、已取代的决定、完成证据和下一步。工具结果与模型自述分别标注。近期工具仅记录名称和宿主报告的成败，不复制原始参数、输出或推理。 |
| 已有会话、回退及重启 | 用会话 ID 和实际压缩点读取记录。重启后台后可在原会话继续。中途才启用插件时，从宿主仍提供的窗口开始；无法核对的历史标作部分覆盖。 |

插件保留 OpenCode 原生压缩流程，数据写入后台为该插件分配的本地存储。输入里已有的私人文字也可能出现在摘录中，并随该会话原本选择的模型收到续接资料。插件自身不请求外部服务，不额外调用摘要模型。主动运行两个工具仍会消耗正常的模型轮次和上下文。

## 使用范围

- 适合一条会话持续推进同一任务。新建会话、其他项目和子代理的历史各自独立。插件运行期间收到会话删除事件时，会清除该会话的插件记录。
- 提醒是有长度限制的历史资料。尚未观察到的阶段成果、摘录省略的细节，以及早期未被记录的历史不能凭空恢复。关键外部动作仍要依据实际结果和当前授权判断。
- 默认后台摘要可能先生成、稍后才采用。插件按宿主保留的助手消息和实际压缩点关联这段历史。投递事件缺失或回退后无法核对时，保留可确认的前段并标明缺口。工具回执和进度以插件看到的结构化消息为准。
- 对使用加密压缩项的模型，只在可确认的宿主替换窗口之后加上提醒。原生窗口不能匹配时跳过。此分支有结构测试；尚未对商业模型的原生压缩或 Windows 后台做实机验收。

## 安装与停用

从本目录运行 `npm pack --ignore-scripts`，解开生成的压缩包，把其中的 `package` 文件夹改名为 `long-conversation-loop`。放到运行 OpenCode 后台一侧的插件目录，macOS 默认为 `~/.config/opencode/plugins/`，Windows 默认为 `%USERPROFILE%\.config\opencode\plugins\`。若自定义了 `XDG_CONFIG_HOME`，使用其下的 `opencode/plugins/`。包只用 Node 内置模块，无需安装 npm 依赖。下一次启动后台时加载。要停用，移出这个插件目录，再由后台重新加载。

## 验证与复跑

运行 `npm test` 检查多次压缩、历史分页、输入来源、回退与会话隔离。macOS 上还可以运行以下命令，用 Desktop 捆绑的后台和回环地址的固定回复模型做端到端验证。

```sh
python3 -B test/host_probe.py /Applications/OpenCode.app/Contents/Resources/opencode-cli
```

固定回复模型会故意在摘要里丢掉目标和撤回授权。脚本比较原生与启用插件后的真实模型请求，覆盖连续手动压缩、默认后台摘要的采用、阈值触发的自动压缩、前后排队与取消、调用工具和重启原会话。测试使用临时配置与合成会话，进程退出时释放。它验证资料是否到达模型；真实模型持续遵循约定的比例和缓存开销仍待对照测量。

### Kimi 与 MiMo 的首轮实测

2026-11-25，macOS，OpenCode 2.4.0，插件 `0.1.0-alpha.1`。在隔离后台导入同一份 24 轮合成记录，再触发手动压缩。预先规定八项答案，按字段、值和类型逐一判分。原始外发授权被撤回，场地和预算在中途修改，纸样已验收，成品待验收。Kimi 在第一次压缩后又收到了更换联系人的要求。最后一次进度询问临时将交接份数改为一份。

| 模型 | 压缩及作答条件 | 正确字段 |
|---|---|---:|
| Kimi K3.1 Pro | 原生摘要，两次压缩，插件关闭 | 8/8 |
| Kimi K3.1 Pro | 原生摘要，两次压缩，插件开启 | 8/8 |
| MiMo V2.6 Flash | 原生摘要，一次压缩，插件开启 | 8/8 |
| Kimi K3.1 Pro | 将同一份末轮请求的原生摘要及其近期记录替换为缺项摘要，移除插件提醒 | 1/8 |
| Kimi K3.1 Pro | 以上相同请求，保留插件提醒 | 7/8 |

Kimi 在缺项摘要下单靠末轮要求答对了份数。加入提醒后，还答对目标、场地、预算、纸样回执、联系人和当前外发权限。第 3 条提示中的封签编号仅在归档中。另开一例允许一次回查，Kimi 选择了 `loop_recall`，查询串为「纸袋 封签 底纹 编号 seal」，没有匹配，最终填写 null。使用同一批归档在本地复核，单查「封签」或确切编号均能定位第 3 条。该版本只支持连续子串匹配。

四个试验共取得 14 次成功的真实生成，其中 Kimi 12 次、MiMo 2 次。另有一次 Kimi 请求返回 HTTP 404，未取得回复，排除在评分外。为使用既有模型连接，测试通过 OpenCode 的一次性文本接口传送带角色标签的有序消息；回查专项把模型选择转换成工具调用，交给隔离后台执行。每个条件只测一次。这轮没有测自然耗尽上下文、服务商原生多角色传输、真实工具多次重试或账单缓存。

**多关键词修复复测（alpha.2）。** 在相同的 24 轮合成会话中，压缩摘要和默认提醒都没有封签编号。Kimi K3.1 Pro 自行选择 `loop_recall`，给出关键词「封签 底纹」和上限 24。工具返回第 3 条原话「标签底纹样片在纸袋里。纸袋上的封签底纹编号为 S8Q-41。」Kimi 随即答出 `S8Q-41`。这一次共两次真实生成、一次工具调用。另用上次失败的五词查询做固定回归，即使其中的英文词没有出现在原话里，也能找到同一条记录。

复跑使用 [live_models.py](test/live_models.py)。先用 `opencode models` 找到目标模型前面的服务商 ID。以下以 Kimi 原生组为例，另外三组可选 `kimi-plugin`、`kimi-recall` 和 `mimo-plugin`。显式传入 `--live` 会使用所选模型的额度。

```sh
python3 -B test/live_models.py kimi-control --provider '你的服务商ID' --live
```

宿主机制可对照 [2.4.0 压缩实现](https://github.com/anomalyco/opencode/blob/44aed4fd144611879046ae923c25541f913780ad/packages/core/src/session/compaction.ts)、[事件定义](https://github.com/anomalyco/opencode/blob/44aed4fd144611879046ae923c25541f913780ad/packages/schema/src/session-event.ts) 和 [请求准备流程](https://github.com/anomalyco/opencode/blob/44aed4fd144611879046ae923c25541f913780ad/packages/core/src/session/model-request.ts)。

### 压缩后续写与原话回查的缓存实测

2026-11-25，OpenCode Desktop 2.4.0，续接插件 alpha.2。原生右栏「上下文 → 缓存 Token」取最近一条带用量的助手消息，依次显示缓存读取和写入。压缩或撤销会改变取值范围。以下按输入 token 加权，命中率为缓存读取量除以未缓存输入、缓存读取和缓存写入之和。[原生侧栏源码](https://github.com/anomalyco/opencode/blob/44aed4fd144611879046ae923c25541f913780ad/packages/gui-plugins/src/context/tab.tsx#L117-L130)

**原生会话续写。** 导入相同的 24 轮合成历史和固定压缩摘要。提醒组通过发布版的捕获和注入函数生成原文，再将它加入测试会话。两组分别连续发送三条相同的短提示，禁用工具，从各轮助手消息直接取数。表中三轮分别列「缓存读取 / 总输入」，全部请求的缓存写入字段均为 0。

| 模型 | 条件 | 压缩后第 1 轮 | 第 2 轮 | 第 3 轮 | 后两轮合计命中率 | 全三轮合计命中率 |
|---|---|---:|---:|---:|---:|---:|
| Kimi K3.1 Pro | 仅摘要 | 0 / 1,048 | 1,048 / 1,126 | 1,126 / 1,190 | 93.87% | 64.63% |
| Kimi K3.1 Pro | 摘要和提醒 | 768 / 1,444 | 1,444 / 1,530 | 1,530 / 1,591 | 95.29% | 81.97% |
| MiMo V2.6 Flash | 仅摘要 | 0 / 1,027 | 1,024 / 1,072 | 1,024 / 1,116 | 93.60% | 63.70% |
| MiMo V2.6 Flash | 摘要和提醒 | 0 / 1,463 | 1,408 / 1,510 | 1,472 / 1,551 | 94.09% | 63.66% |

加入提醒后，首轮总输入分别增加 396 和 436 个 token。每个条件只有一组，Kimi 先测仅摘要，MiMo 先测带提醒。服务端预热不可控，尤其是 Kimi 的提醒组首轮已经命中 768 个 token。这组数据只覆盖重复续写，未测生成压缩摘要的开销。

**封签回查。** 使用上一轮的隔离后台、真实插件及第 3 条原话，改用官方会话生成接口取每次请求的用量。Kimi 自行回查，选择工具和读取结果后作答分别命中 768 / 4,999 和 768 / 4,983，合计 15.39%，正确答出 `S8Q-41`。MiMo 首次生成命中 0 / 5,133，直接答 `null`，未发起回查。这个用例把带角色的历史序列化成文本，首次还在文本前附上工具说明，第二次不再附加。两次请求的前缀不同，结果适用于这条测试链路；日常 Desktop 原生工具调用的命中率仍需单独测量。

复跑时向 [native_cache.py](test/native_cache.py) 提供已知服务商 ID。可选模型为 `k3.1-pro` 和 `mimo-v2.6-flash`，加 `--recall` 切换到封签回查。脚本使用官方 CLI 已有的模型连接，显式加 `--live` 才会产生真实模型请求。结束时归档本轮新建的计量会话。

```sh
python3 -B test/native_cache.py --model k3.1-pro --provider '你的服务商ID' --live
```

### 一次真实研究会话的自然压缩

2026-11-26，在 macOS 的 OpenCode 2.4.0 中，Kimi K3.1 Pro 主持了一次长程插件审核，Kimi 和 MiMo Flash 分别承担子任务。主会话记录了一次已完成的原生自动压缩。压缩前最后一个模型步骤计量为 887,398 token，压缩后第一个步骤为 39,830 token。这两个读数是相邻步骤的观测值，触发判断还会计入其后新增内容的估算。

压缩后，仅给出两条早期追加要求的主题，请模型找回序号、消息 ID 和全文。两条都早于宿主保留的尾段，原生摘要也没有收录它们的全文或 ID。Kimi 自行调用 `loop_recall`，最终回答与第 2、4 条原始输入逐字一致。一次宽泛搜索返回了其他消息，更具体的查询找到了目标。本次只验证了 Kimi 主会话的一次自然压缩；跨多次压缩的恢复率及关闭插件时的差异仍待实测。

## 跨对话协作候选版

在同一台电脑、同一工作目录中，OpenCode 和 Codex 可以互留问题、回复和阶段进度。双方各自在自己的对话里说「加入导出任务，我叫主线／审核，与审核／主线配对」。选择要共享的进度字段后，可以问「审核还有什么待决定的问题」。对方退出后仍可收件。切换工作树会进入另一个独立工作区。

交换部分需要 PATH 中的 Python 3（建议 3.10 以上）和标准库 SQLite。共享功能首次加入时创建本地 `.ai-loop/exchange/v1/mailbox.sqlite3`。每一端默认只分享显式留言。可向指定人共享本会话的下步、限制、完成项。更正、撤回、回复保留历史。共用此工作区的本机账户可以访问库文件。请选本地磁盘，跨设备复制请在两端停用后进行。

工具为 `loop_exchange`。它按登记的工作目录和实际会话绑定身份。恢复已登记的后端会话、或采用新的压缩摘要后，有未确认变更时给出一句提醒；压缩导致协作上下文丢失时，提供回查已确认记录的提示。同一后端持续运行时重新聚焦一个窗口，可直接要求同步。协作协议约束通过工具提交的操作。用户的当前指令仍然优先。
